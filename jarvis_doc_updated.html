01Overview

Jarvis is a voice-first personal assistant that runs entirely on a Windows desktop or laptop. It listens for a wake word, transcribes speech in real-time via streaming STT, classifies the user's intent through a five-tier cascade (regex → semantic → keyword NLP → function calling → LLM chat), runs the matched command through an NLU entity-extraction layer, and either executes a desktop action instantly with a voice-optimized template response, or falls back to a local LLM running through Ollama. A dialogue state machine manages follow-up windows so the user can continue speaking without repeating the wake word, and a concurrent pipeline overlaps STT with intent detection for sub-second command execution.

The architecture is designed around four core principles:

Four Design Principles

  1. Latency over perfection. A regex match in 0 ms beats a perfect LLM answer in 4 seconds. The intent router is layered so the cheapest path that works wins. Early intent execution fires simple commands before the user finishes speaking.
  2. Graceful degradation. Every cloud service has a local fallback. Every optional package fails silently into a working alternative. The assistant never crashes from a missing dependency.
  3. Hardware adaptation. The LLM model is auto-selected at startup based on available RAM and GPU. The same code runs on an i5 with 8 GB and an i9 with 32 GB — just with different model sizes.
  4. Voice-first responses. Action confirmations use bilingual templates (no LLM call needed — instant). LLM responses are constrained to 1–4 spoken sentences with no markdown. Every user-facing string exists in both English and Egyptian Arabic.

The 30-second mental model

Think of Jarvis as a six-act play with a stage manager (the Dialogue Manager) deciding the flow. Audio streams in real-time through a concurrent pipeline where STT, intent detection, and live-data prefetching run in parallel. 05Startup Sequence

Before the first wake-word detection, Jarvis runs a parallel prewarm sequence that loads all heavy models into RAM. This trades startup time (5–15 seconds) for latency on the first user interaction (which would otherwise be ~10s).

What happens when you run python main.py

Figure 5.1 — Startup timeline. Sequential prewarm path is used on low-core machines to reduce peak memory usage.
Why prewarm matters
Without prewarm, the first time the user says "Jarvis", the assistant would have to load the 600MB Whisper model from disk (~3s), then the 2.5GB Qwen3 model (~5s), then the semantic router (~3s) — adding ~11 seconds of latency to the first interaction. With parallel prewarm at startup, the first user interaction is just as fast as the hundredth.

07Stage 2 — Audio Capture (Streaming VAD)

Once the wake word fires, Jarvis begins streaming audio capture with concurrent STT. The new audio/streaming_stt.py module replaces the old record-then-transcribe approach: audio chunks are processed in real-time through Silero VAD for speech detection, and partial transcripts are emitted while the user is still speaking — enabling early intent detection and parallel processing.

How streaming VAD works

  1. Open a 16kHz mono input stream via sounddevice
  2. Read 512-sample chunks (~32ms each) into a ring buffer
  3. Each chunk runs through Silero VAD (1.2MB ONNX, ~2ms per chunk) — with an energy pre-filter that skips Silero inference on pure silence to save CPU
  4. Maintain a pre-roll buffer (configurable, default ~200ms) so the start of speech isn't clipped
  5. Once speech is detected, captured chunks are fed to Whisper via a background thread every ~0.45s, emitting partial transcripts via on_partial(text) callback
  6. Adaptive silence timeout: command mode (0.55s after wake word) vs chat mode (1.0s during follow-up window) — configurable
  7. Hard cap at MAX_RECORD_DURATION (default 6s)
  8. Final transcript is available within ~0.3s of speech ending (vs 1.5–3s in the old batch approach)

Silero VAD vs energy-only

The Silero VAD ONNX model is prewarmed at startup (_prewarm_streaming_vad()). If onnxruntime is not installed or the ONNX model fails to load, Jarvis falls back transparently to energy-threshold VAD. The energy pre-filter still runs in both modes, meaning Silero is only invoked when the chunk has enough energy to plausibly be speech.

08Stage 3 — Speech-to-Text (Streaming + Hybrid)

Jarvis uses a streaming-first STT strategy. During audio capture, audio/streaming_stt.py feeds audio chunks to Whisper incrementally and emits partial transcripts. The final transcript is reused directly — skipping the redundant batch STT pass that used to add 1.5–3 seconds of dead time. If the streaming transcript is unavailable (fallback case), the old hybrid batch path activates: it detects the language, routes Arabic to ElevenLabs and English to local Faster-Whisper.

Streaming partial stability

The streaming engine now treats Arabic and English differently. English partials can emit as soon as they change, but Arabic partials pass through a stability gate: the same Arabic text must appear in two consecutive windows before it is forwarded to early intent detection. This reduces flicker from Whisper's Arabic hypotheses and keeps the concurrent pipeline from firing on unstable fragments. The helper also returns richer metadata, including partial_text, duration_seconds, samples, and a normalized text field for the final result.

Streaming fast-path (new default)

In core/orchestrator.py, when capture_summary["text"] is populated by the streaming engine, the batch STT pass is skipped entirely. The partial transcripts emitted during recording have already been feeding the ConcurrentPipeline for early intent detection. This reduces time-from-speech-end-to-processing from ~2s to ~0.3s.

09Stage 4 — Intent Routing (5-Tier Cascade)

This is the heart of the assistant's intelligence. Given a transcribed text, it classifies what the user wants. The classifier is structured as a cascade — each tier is faster than the next, and the earliest tier that confidently matches wins. Most commands resolve in tiers 1–3 with zero LLM cost. The new Tier 4 (function calling) handles complex multi-step commands by letting Qwen3 generate structured tool calls via Ollama's /api/chat tools API, while Tier 5 is the pure LLM chat fallback. Phase 4 also added dedicated fast-path parsing for command chaining, advanced file search, and batch file navigation so these requests stay out of the generic LLM flow entirely.

Figure 9.1 — Four-tier intent classification cascade. Numbers are typical distributions across natural usage.

How tiers are wired together

# core/command_router.py — route_command()
parser_candidate = parse_command(text)         # Tier 1 (regex)
parsed = None
nlu_meta = {}

if parser_candidate.intent == "LLM_QUERY":
    semantic_parsed, semantic_meta = _try_semantic_routing(text, parser_candidate)
    if semantic_parsed:                       # Tier 2 (semantic)
        parsed = semantic_parsed
    else:
        keyword_parsed, kw_meta = _try_keyword_nlp_routing(text, parser_candidate)
        if keyword_parsed:                    # Tier 3 (fuzzy keyword)
            parsed = keyword_parsed
        else:
            tool_result = call_tool_tier(text)  # Tier 4 (function calling)
            if tool_result["tool_calls"]:
                parsed = tool_calls_to_parsed_commands(tool_result["tool_calls"])

if parsed is None:
    parsed = parser_candidate                  # Tier 5: LLM_QUERY fallback

# NLU entity extraction (runs on resolved intent, fills missing slots)
nlu_result = NLU().understand(text, intent=parsed.intent, existing_args=parsed.args)
if nlu_result.missing_slots:
    dialogue_manager.set_missing_slots(parsed.intent, nlu_result.missing_slots)
    return response_shaper.get_dialogue("slot_missing_" + nlu_result.missing_slots[0])

NLU entity extraction layer

nlp/nlu.py runs after intent classification. It extracts entities (app names, durations, filenames) from the raw text, handles mixed Arabic/English code-switching via nlp/codeswitching.py, converts Arabic-Indic numerals (٠–٩ → 0–9), and validates required slots. The semantic router now shares an explicit entity taxonomy through nlp/entity_types.py so intents can declare whether they expect an app, path, date, duration, email, person, or system feature. If a required slot is missing (e.g., open_app without an app name), the dialogue manager enters the CONFIRMING state and asks a targeted bilingual follow-up question: "Which app?" / "أي تطبيق؟".

Confidence gating & clarification

After classification, core/intent_confidence.py assesses the result. If confidence is low (e.g., ambiguous "open it"), the router triggers a clarification turn: it stores a pending_clarification in session memory and asks the user to disambiguate. The next utterance is matched against the clarification options before any new parsing.

12Stage 6 — Text-to-Speech (Streaming + Barge-In)

The response is spoken back through neural TTS. This happens in parallel with LLM generation: as soon as the LLM produces the first complete sentence, TTS starts speaking it while the LLM continues generating the rest. For action commands, the response_shaper generates an instant template response (no LLM call) — "Opening Chrome." / "بفتح كروم." — with sub-200ms time-to-first-word.

Arabic sentence buffer

llm/sentence_buffer.py is an Arabic-aware streaming sentence accumulator. For Arabic, it splits on ؟.!\n and soft-flushes at Arabic connectors (و/ف/ثم) after 50 characters or hard-flushes at 100 characters — ensuring TTS speaks natural clauses rather than chopping mid-word. English mode uses standard punctuation splitting.

VAD barge-in monitor

While TTS is playing, the SpeechEngine runs a barge-in monitor that listens for user speech. When the user talks over Jarvis — saying "stop", "وقف", or any word — the TTS is interrupted within ~200ms. The monitor uses an energy-ratio comparison (mic RMS vs expected speaker audio) plus optional Silero VAD confirmation to distinguish real user speech from echo. A 500ms cooldown prevents false re-triggers from echo decay.

Egyptian colloquial rewrite

Before sending Arabic text to TTS, audio/tts.py::_rewrite_to_egyptian_colloquial() applies lightweight phonetic substitutions so the TTS voice sounds natural in Egyptian dialect rather than reading formal MSA.

14 · Memory architecture — what's saved, when, and when it resets

Jarvis has three distinct memory systems: session memory (conversational context, short turns of dialogue, backed by SQLite since Phase 2.8 with JSON fallback), the dialogue state machine (core/dialogue_manager.py, ephemeral, tracks whether Jarvis is idle/listening/confirming/in a follow-up window), and the knowledge base (long-term documents the user has indexed). This section covers session memory and the dialogue manager. The knowledge base is in the next section.

Session memory lives in SQLite (jarvis_memory.db) with a legacy JSON export capability. The core/session_memory.py module is the only writer. Every successful turn appends a row, and context_slots are stored as key-value pairs.

Dialogue state machine

core/dialogue_manager.py manages seven states: IDLE → LISTENING → PROCESSING → CONFIRMING → EXECUTING → RESPONDING → FOLLOW_UP. The key feature: after Jarvis responds, it enters a FOLLOW_UP window (default 10 seconds) during which the user can speak without repeating the wake word. The state auto-expires to IDLE on timeout. During CONFIRMING (asking for PIN or slot-filling), the window is 30 seconds. The should_skip_wake_word() method is the only gate the orchestrator checks.

What's stored in jarvis_memory.json

When memory is written

Every successful turn that produces a non-trivial assistant response triggers a write. add_turn() inside core/command_router.py is the entry point — it runs in route_command() after the action or LLM has returned. Low-value replies (apologies, refusals, empty strings) are filtered out by _is_low_value_assistant_text() so they don't pollute the context.

State-mutating helper methods also persist the file immediately:

  • set_last_app() — when an app is opened or closed
  • set_last_file() — after file operations
  • set_pending_clarification() / clear_pending_clarification()
  • set_response_mode(), set_stt_profile(), set_audio_ux_profile()
  • record_clarification_preference() — when user picks one of N options
  • record_app_usage() — increments app_usage[name]

When memory is read into the prompt

In llm/prompt_builder.py → build_prompt_package():

  1. session_memory.build_context(max_chars=900) — last few LLM_QUERY turns in the same language, formatted as compact "USER: …\nASSISTANT: …" lines.
  2. session_memory.context_snapshot() — extracts last_app, last_file, pending_confirmation_token as a one-line CONTEXT: string.

Both are skipped for the lightweight prompt path (≤8-word queries with no recent context) — that path goes straight to a sub-15-line system prompt.

When memory resets

TriggerWhat gets cleared

Important
The 10-turn rolling window means Jarvis remembers up to 10 recent exchanges across restarts. After the 11th turn, the 1st turn is gone forever. There's no long-term conversation memory by design — for that, use the knowledge base (next section).

15 · Live data fetching — when Jarvis hits the internet

By default, Jarvis runs offline. The local LLM has no internet access — it can't tell you today's weather, today's news, or today's prices. Asking it directly produces stale knowledge or generic apologies.

To fix that, the router runs a marker-based pre-LLM hook that fetches live data from two free APIs and injects results into the prompt as a LIVE DATA: block. The LLM sees real, current information and answers from it.

The data flow

Triggers — what actually fires the fetch

Defined in core/command_router.py as substring marker sets. If any marker appears in the normalized user text, the matching tool is called.

web_search.py _NEWS_QUERY_MARKERS news, headline, breaking, today news, اخبار, خبر, العناوين, عاجل

How fetched data reaches the LLM

If the tool returned a non-empty string, build_tool_augmented_prompt() is called instead of the regular package. The system block stays minimal, then a LIVE DATA: block is inserted right before the user query:

SYSTEM:

Never refuse safe questions.

LIVE DATA (use this to answer):
Weather in Cairo: Clear sky, 24°C, humidity 38%, wind 12 km/h

USER:
ايه حالة الجو النهارده؟

ASSISTANT:

Direct-answer fast path

For weather queries specifically, _direct_live_data_answer() bypasses the LLM entirely and returns the formatted weather string directly. This is faster and more reliable for a weather lookup, since the LLM adds no value — the API output is already user-facing.

When fetching is skipped

  • Tool import fails (e.g. ddgs not installed) — exception is logged, fetch returns empty string, LLM proceeds without live data.
  • API request times out (5s for weather, longer for search) — same as above.
  • WEB_SEARCH_ENABLED=false in config.
  • An action handler matched first (regex/semantic/keyword tier) — by then the router has already returned and never reaches the LLM block.

16 · Knowledge base — long-term documents the user has indexed

Separate from session memory, the knowledge base is for documents the user explicitly wants Jarvis to remember and reference: notes, manuals, project docs, transcripts. Implemented entirely in core/knowledge_base.py.

How a document gets indexed

Configuration

KB_EMBEDDING_MODELall-MiniLM-L6-v2~90 MB on disk. ~180 MB RAM when loaded.
KB_EMBEDDING_DIM256 (truncated from 384)Smaller index, faster search, minimal accuracy loss.
KB_CHUNK_SIZE600 charsEach chunk is one passage of context.
KB_CHUNK_OVERLAP120 charsEnsures no concept is split clean across chunks.
KB_TOP_K3Top 3 chunks retrieved per query.
KB_MAX_CONTEXT_CHARS1400Cap on total injected KB context length.
KB_MIN_PROMPT_SCORE0.45Cosine score threshold; below this, KB context is dropped (irrelevant).

How retrieval works on each LLM query

Inside build_prompt_package():

  1. knowledge_base_service.retrieve_for_prompt(query, top_k=3, max_chars=1400) is called.
  2. The query is embedded with the same MiniLM model.
  3. Cosine similarity computed against all chunk vectors (FAISS or numpy).
  4. Top 3 chunks above KB_MIN_PROMPT_SCORE (0.45) are selected.
  5. A lexical re-rank applies (35% weight lexical, 65% semantic).
  6. Selected chunks are concatenated up to 1400 chars and injected as KNOWLEDGE: … in the prompt.
  7. Source filenames are kept for citation (if LLM_APPEND_SOURCE_CITATIONS is on).

Voice commands for KB management

CommandAction
kb add <path>Index a single file (.txt, .md, .pdf with pypdf)
kb index <dir>Recursively index a directory
kb sync <dir>Re-index changed files only (uses content_hash + mtime)
kb search <query>Show top matching chunks (no LLM call)

When the KB resets

  • Manually deleting the .jarvis_kb/ directory.
  • Files indexed and then deleted from disk are not auto-removed from the index — content is preserved by hash.
  • Re-indexing the same file with changed content removes the old chunks and inserts new ones (via _remove_source_chunks_locked).
  • Sync mode skips unchanged files (hash + mtime match) to avoid wasted embedding work.
KB vs session memory
Session memory is a 10-turn conversation buffer that resets often. The knowledge base is permanent storage of explicitly indexed documents — it never resets unless the user deletes the folder. Both feed into the same LLM prompt, but they answer different questions: "what did we just talk about?" vs "what does this document say?"

How auto-selection runs

Inside core/orchestrator.py → _detect_and_set_runtime_model():

  1. If JARVIS_LLM_MODEL is set to a non-default value, treat as manual override and use it as-is.
  2. Otherwise query system resources via psutil (RAM, CPU cores) and query Ollama's /api/ps for GPU availability.
  3. Pick the smallest Qwen3 variant that fits comfortably in RAM. If multiple choices are viable, prefer the higher-quality model.
  4. Set prewarm strategy: if cpu_count() ≤ 4 then sequential prewarm is used to avoid contention (see core/orchestrator.py changes). Otherwise a parallel ThreadPoolExecutor prewarm is used.
  5. Record chosen model and prewarm strategy in metrics and the startup audit log.

    1. Slim the system block in prompt_builder.py further (#1 above) — directly drives LLM quality.
    2. Replace the AR wake layer with a real wake-word ONNX (#3) — directly drives wake reliability.
    3. Stop the post-processing pipeline from calling the LLM (#2) — directly drives latency and consistency.

    16Knowledge Base

    A local document store with semantic search, separate from session memory. You add files (txt, md, py, json, csv, pdf), the system chunks them, embeds the chunks with a multilingual model, stores them on disk, and at query time retrieves the most relevant chunks to inject into the LLM prompt.

    Storage layout — .jarvis_kb/

    FileFormatPurpose
    meta.jsonJSON array of recordsOne record per chunk: id, source path, chunk_index, text, hash, indexed_at
    vectors.npyNumPy float32 arrayShape (N, 384) — one row of embeddings per chunk. Loaded into RAM at startup.
    index.faissFAISS binary (optional)IndexFlatIP for fast cosine search. If faiss-cpu not installed, falls back to numpy dot-product loop.
    sources.jsonJSON objectPer-source state: content_hash, mtime, chunk_count, indexed_at. Used for incremental re-index.

    Indexing flow

    Retrieval flow at LLM-query time

    From core/knowledge_base.py:retrieve_for_prompt():

    1. Embed the user query → 384-dim vector.
    2. FAISS (if available): index.search(query_vec, top_k * rerank_multiplier) returns scored candidates. If FAISS not installed: numpy dot-product over all vectors (still fast under ~10K chunks).
    3. Hybrid rerank: combine KB_EMBEDDING_RERANK_WEIGHT · cosine_score with KB_LEXICAL_RERANK_WEIGHT · token_overlap_score. Defaults are 0.7/0.3.
    4. Drop candidates below KB_MIN_PROMPT_SCORE (default ~0.35).
    5. Drop chunks matching KB_BLOCKED_CONTEXT_PATTERNS (regex blocklist — prevents prompt-injection by indexed documents).
    6. Strip suspicious prefixes ("system:", "assistant:") from chunk text — defense against injected role tokens.
    7. Concatenate top-K chunks until KB_MAX_CONTEXT_CHARS reached.
    8. Return: context string + sources list + raw results.

    18Hardware Tiers

    At startup, core/hardware_detect.py reads total RAM and probes Ollama for GPU availability, then picks the best Qwen3 model that fits. You can disable auto-select with JARVIS_LLM_AUTO_SELECT=false and pin a model in JARVIS_LLM_MODEL.

    Tier table (from _MODEL_TIERS in core/hardware_detect.py)

    Tier RAM GPU Model num_ctx lightweight num_ctx Realistic gen speed
    high ≥16 GB Yes qwen3:8b 8192 4096 40-60 tok/s
    medium ≥12 GB Any qwen3:4b 4096 2048 12-18 tok/s CPU · 35-50 tok/s GPU
    medium 8 GB Yes qwen3:4b 4096 2048 30-45 tok/s GPU
    low 8 GB No qwen3:1.7b 2048 1024 20-30 tok/s
    minimal <8 GB Any qwen3:0.6b 1024 512 40-60 tok/s

    How GPU detection works

    From detect_gpu_available() in core/hardware_detect.py: query GET /api/ps on Ollama. If any returned model has size_vram > 0, GPU is available. This is the most reliable cross-platform check — it works for CUDA on Windows/Linux, ROCm on Linux, and Metal on macOS without us shipping a per-platform GPU SDK.

    Caveat: if Ollama hasn't loaded any model yet, the check returns False. The orchestrator runs detection after ensuring Ollama is up but before first model load — so the very first run may be classified as no-GPU even on GPU machines. Restart once and it self-corrects.

    Manual override

    # In .env — pin the exact model regardless of hardware:
JARVIS_LLM_MODEL=qwen3:4b
JARVIS_LLM_AUTO_SELECT=false
JARVIS_LLM_OLLAMA_NUM_CTX=4096
JARVIS_LLM_LIGHTWEIGHT_NUM_CTX=2048

    If JARVIS_LLM_MODEL differs from the hardware default, the orchestrator treats it as manual_override and skips auto-select even when AUTO_SELECT=true. Logged as selection_reason=manual_override.

    Auto-pull on first run

    After tier selection, _ensure_model_available() queries GET /api/tags to see if the chosen model exists locally. If not, it streams POST /api/pull until complete, logging progress every ~5 seconds. No manual ollama pull needed.
